# Audit Sumi Docs

Return one compact, findings-first audit of the live target. Treat the audit as
read-only: do not modify source, configuration, Git state, GitHub state, or host
state; do not install or update tools. Repository validation may refresh only
its normal ignored build outputs. Return the report to the caller by default.
Write a report only when the user names an ignored `artifacts/` destination.

## Bind the evidence snapshot

Read the root and nearest nested `AGENTS.md` before selecting checks. Resolve
the target rather than inferring it from an earlier report:

```powershell
git rev-parse --show-toplevel
git rev-parse HEAD
git branch --show-current
git status --porcelain=v2 --branch
node --version
pnpm --version
```

Record the UTC timestamp, operating system, target path, HEAD, branch, tree
cleanliness, tool versions, commands, exit codes, and skipped checks. Inspect
staged, unstaged, and untracked paths when the tree is dirty. Attribute results
to `HEAD` only for a clean tree; otherwise identify the audited snapshot as
`HEAD` plus the listed worktree changes and keep commit evidence separate from
worktree evidence.

Use current source, tests, generated artifact contents, GitHub checks, and live
probes in that order of relevance. Treat `docs/history/` and package history
snapshots as non-authoritative. Redact secret values and machine-specific
absolute paths from the report.

## Select the audit profile

- For a repository health audit, cover every applicable ownership boundary and
  run the root validation gates.
- For a release-candidate audit, also bind the candidate commit and artifacts,
  inspect the current candidate workflow and public checks, and verify the
  packaging, compliance, performance, publication, and rollback evidence that
  the candidate claims.
- For an architecture consistency audit, trace each affected contract from its
  authority through generated projections, consumers, tests, and operational
  documentation. Do not replace runtime evidence with an architecture diagram.
- For a PR, commit, or branch diff, use `$sumi-docs-pr`. For a security-only
  scan, use the available security audit workflow. For a single failure, run a
  focused diagnosis rather than expanding it into a repository audit.

Do not run a generic checklist. Select dimensions from the target and change
surface, and mark inapplicable dimensions explicitly.

## Follow repository authority

Review these contracts when applicable:

1. `docs/` and `apps/web/src/content-catalog.ts` are the reviewed content and
   navigation authority. Verify English and Chinese pairing, catalog coverage,
   route stability, and that Web and MCP projections derive from the same
   reviewed source without sharing an MDX trust model.
2. Preserve manifest v1 while verifying canonical, digest-addressed, immutable
   v2 locator and snapshot behavior. Check generated bytes and routes rather
   than comparing prose descriptions alone.
3. Verify the four public tools and their schemas across stdio and stateless
   Streamable HTTP. Check the installed MCP 2026 protocol header, JSON-RPC error
   behavior, sanitized diagnostics, Host and Origin policy, lifecycle, and
   readiness contracts. Do not confuse a local directory, remote corpus URL,
   human site URL, MCP endpoint, or readiness URL.
4. Verify local and bounded remote corpus acquisition independently. Confirm
   path containment, URL and redirect restrictions, size and time bounds,
   content integrity, process-local snapshot semantics, and restart behavior.
5. Verify thin Codex, Claude Code, and VS Code host adapters against the exact
   repository allowlist. Project Skills may route workflows but must not own
   mutable session state or expand MCP filesystem authority.
6. Verify the pinned pnpm and Node versions, TypeScript boundaries, Oxlint,
   Prettier, TypeDoc routes, duplicate-code policy, Starlight navigation, and
   i18n using the repository's owned commands and configurations.
7. Verify Docker and Postman examples, candidate packaging, SBOM, NOTICE,
   dependency provenance, SEA output, checksums, and human acceptance gates
   only when that delivery surface is in scope.
8. Distinguish a successful static Pages publication from an optional remote
   MCP deployment. When `PUBLIC_MCP_URL` and
   `PUBLIC_MCP_READINESS_URL` are configured, require their paired fail-closed
   binding and revision evidence; when absent, do not claim a public MCP
   endpoint or require `_mcp/server.json` to exist.
9. Treat protected `main`, pull-request policy, least-privilege workflows, and
   immutable candidate evidence as separate gates. A green build does not
   authorize merge, tag, package publish, deployment, or release.

## Execute owned checks

Prefer existing package and root scripts; do not create an audit engine or
install optional scanners. Start with the smallest red test for an observed
failure. For a full health or candidate audit, run from the repository root:

```powershell
pnpm run verify
pnpm run verify:integration
git diff --check
```

Use `pnpm --filter <package> <script>` for a scoped package audit. For a
candidate, read `.github/workflows/candidate.yml` and `docs/releasing.md`, then
run only the exact current SEA, smoke, pack, compliance, and benchmark commands
required by those contracts. Record benchmark runtime, hardware, executable,
iterations, distribution statistics, policy baseline, and exit status. Never
infer latency, coverage, complexity, vulnerability, or reliability from source
shape or a single successful run.

Use network and GitHub reads only when the audit asks about current remote or
publication state. Record the exact URL, revision, probe time, response status,
and relevant headers or hashes. Do not mutate issues, pull requests, branch
rules, workflows, releases, variables, deployments, or packages.

## Calibrate findings

Classify every candidate as `confirmed`, `likely`, `rejected`, or `unknown`.
Require a reproducible evidence chain before using `confirmed`. State missing
evidence and the next discriminating check for `unknown`; retain rejected
candidates only when they prevent a plausible false positive from resurfacing.

Order findings by severity, then confidence. Each finding must include:

- status, severity, confidence, owner, and affected surface;
- impact and preconditions;
- repository-relative source, test, command, check, artifact, or live-probe
  evidence;
- the contract or invariant that is violated;
- a bounded remediation direction;
- verification and rollback criteria.

Use `critical`, `high`, `medium`, `low`, or `informational` severity only where
the impact supports it. Do not assign a 0-100 score, letter grade, model or
agent signature, fictional approval, fixed 30-day roadmap, default person-day
estimate, generic industry comparison, or unmeasured quality claim. Do not use
emoji or labels such as `SOTA` or `production-ready` without an owned rubric
and complete evidence.

## Report once

Return this compact structure:

1. **Findings**: ordered finding records with direct evidence. If none are
   confirmed, say so explicitly.
2. **Evidence boundary**: target, timestamp, HEAD, dirty-state attribution,
   environment, commands, remote probes, and exclusions.
3. **Passed contracts**: only gates actually executed or directly inspected.
4. **Unknowns and residual risk**: failed, skipped, unavailable, stale, or
   incomparable evidence, even when no findings were confirmed.
5. **Next decisions**: the smallest owner-assigned actions and their
   verification and rollback conditions.

Do not create `README`, `AUDIT-COMPLETE`, scorecards, per-dimension reports, or
other report bundles. Do not copy repository discussion, abandoned proposals,
or tool provenance into product files.
